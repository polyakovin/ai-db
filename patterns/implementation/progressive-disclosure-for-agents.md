# Progressive disclosure для AI-агентов

Progressive disclosure — паттерн поэтапной подачи контекста: агент сначала видит компактный каталог возможностей, затем загружает инструкции выбранной возможности и только после этого читает или исполняет ресурсы, необходимые для конкретного шага. Цель — не скрыть знания, а дать модели минимально достаточную информацию в момент принятия каждого решения.

## Проблема

Если заранее поместить в prompt все skills, tool schemas, проектные правила и справочники:

- служебный контекст вытесняет задачу и рабочие данные;
- похожие инструкции начинают конкурировать;
- модели сложнее выбрать релевантную возможность;
- растут стоимость запроса и цена cache miss;
- монолитные инструкции быстрее устаревают и хуже проверяются.

Противоположная крайность тоже опасна: если стартовый каталог слишком бедный, агент не узнает о нужном материале и не запросит его. Progressive disclosure работает только при качественной маршрутизации и наблюдаемой загрузке.

## Решение: три уровня раскрытия

| Уровень | Что видит модель | Когда загружается | Задача уровня |
|---|---|---|---|
| 1. Discovery | имя, точное описание, триггеры, категория | при старте или перед выбором возможности | понять, **что существует и когда это выбирать** |
| 2. Activation | основной workflow, ограничения, критерии завершения, карта ресурсов | после совпадения с задачей | понять, **как действовать** |
| 3. Execution | reference-файлы, schemas, примеры, scripts, assets, retrieved chunks | по условию конкретного шага | получить **детали, нужные сейчас** |

Официальная [спецификация Agent Skills](../../sources/libraries-tools/agent-skills-specification.md) использует эту модель для `SKILL.md`: metadata загружается для всех skills, тело выбранного skill — после активации, дополнительные файлы — по мере необходимости. Тот же принцип применим к tools, документации репозитория и retrieval.

```text
base_context = stable_rules + capability_catalog.metadata
matches = select(task, capability_catalog)

for capability in matches:
    guide = load(capability.entrypoint)
    follow(guide)

    if guide.requires(resource, current_step):
        details = load(resource)
        continue_with(details)
```

Ключевой инвариант: следующий уровень загружается по наблюдаемому сигналу — совпадению с задачей, выбранной ветке workflow или потребности в конкретном ресурсе, а не «на всякий случай».

## Архитектурные элементы

### Компактный индекс

Индекс должен позволять принять решение без чтения полного материала. Для каждой возможности нужны:

- однозначное имя;
- что она делает;
- когда её применять и когда не применять;
- ключевые термины из пользовательских запросов;
- ссылка на одну точку входа;
- при необходимости — класс риска или требуемый permission.

Описание вида «помогает с документами» почти бесполезно: оно создаёт и false positives, и false negatives. Хорошее описание перечисляет действие, типы входов и наблюдаемые триггеры.

### Точка входа как карта

Основной файл — не склад всей документации, а исполнимая карта:

1. обязательный baseline;
2. порядок действий;
3. развилки и условия;
4. проверки результата;
5. прямые ссылки на дополнительные ресурсы.

Критические инструкции, без которых любое выполнение небезопасно или неверно, должны находиться здесь или в always-on policy. Их нельзя прятать в файл, который агент может не открыть.

### Ресурсы по границам решений

Дополнительные материалы лучше делить не по произвольному размеру, а по вопросам, возникающим в workflow:

```text
invoice-processing/
├── SKILL.md
├── references/
│   ├── extraction.md
│   ├── validation.md
│   └── tax-rules.md
├── scripts/
│   └── validate-invoice.py
└── assets/
    └── output-template.xlsx
```

Если задача требует только извлечения полей, `tax-rules.md` не должен попадать в контекст. Ссылки лучше держать на один переход от точки входа: длинная цепочка `SKILL.md → advanced.md → details.md` повышает риск частичного чтения или пропуска важной детали.

### Loader и граница контекста

Файл, schema или tool действительно считаются отложенными, только если их содержимое отсутствует в model context до выбора. Хранение материала в отдельном файле само по себе ничего не даёт, если runtime всё равно сериализует его в prompt.

Loader должен:

- загружать только выбранный ресурс;
- сохранять источник и версию;
- учитывать context budget;
- не дублировать уже загруженное без причины;
- логировать причину выбора;
- возвращать понятную ошибку, если ресурс недоступен.

## Где применять

### Skills

Заранее показывать metadata всех skills, полный `SKILL.md` читать после совпадения, а references и scripts использовать по ветке workflow. Спецификация Agent Skills рекомендует держать основной файл короче дополнительных материалов: ориентир — менее 5 000 токенов инструкций; конкретный лимит нужно проверять evals, а не считать универсальной гарантией.

### Каталоги tools и MCP

Небольшой набор частых или критичных tools можно оставить always-on, а длинный хвост искать и раскрывать по запросу. После discovery агенту передаётся полная schema только найденных tools. Это снижает контекстный шум, но не заменяет permissions и approval.

### Документация репозитория

Корневой `AGENTS.md` или `README.md` служит картой, domain-документы раскрывают локальные правила, а подробные references читаются для конкретного изменения. Этот вариант описан в [Harness Engineering](../../sources/research-production/harness-engineering-openai.md): небольшой стабильный вход ведёт к versioned knowledge store вместо монолитной инструкции.

### RAG и большие справочники

На первом уровне агент видит карту коллекций или доменов, затем выбирает источник, после чего retrieval возвращает только релевантные chunks. Progressive disclosure определяет **когда и на каком уровне открывать детали**, а [RAG](../architecture-design/rag-for-agents.md) — **как найти фрагменты во внешнем корпусе**.

## Правила проектирования

1. **Описывайте маршрутизацию.** Metadata отвечает одновременно на вопросы «что делает?» и «когда применять?».
2. **Держите always-on слой коротким и стабильным.** Туда входят только общие invariants, карта и правила безопасности.
3. **Загружайте минимальный достаточный набор.** Не весь домен, а материалы выбранной ветки.
4. **Делайте ссылки прямыми.** Точка входа должна ссылаться на каждый доступный ресурс без глубоких цепочек.
5. **Формулируйте условия загрузки.** Например: «при tracked changes прочитать `redlining.md`».
6. **Не откладывайте trust boundaries.** Discovery сообщает о capability, но не выдаёт разрешение на её использование.
7. **Отделяйте инструкции от данных.** Retrieved content остаётся недоверенными данными, даже если загружено через доверенный индекс.
8. **Наблюдайте за выбором.** Логируйте candidate set, activation, прочитанные ресурсы, token cost и итог.

## Когда не применять

Progressive disclosure не нужен или вреден, если:

- возможностей мало, их определения короткие и почти все нужны в каждом запросе;
- дополнительный lookup дороже экономии контекста в latency-critical workflow;
- информация является обязательной policy и должна действовать всегда;
- runtime не умеет выборочно загружать контент;
- качество каталога и selector нельзя тестировать или наблюдать.

В этих случаях проще держать небольшой статический контекст. Паттерн окупается при росте числа возможностей, размере их инструкций или различии доменов.

## Типовые ошибки

| Ошибка | Последствие | Исправление |
|---|---|---|
| расплывчатое описание | нужный skill или tool не активируется | добавить действия, типы входов и trigger terms |
| слишком широкое описание | лишние активации и конфликт инструкций | указать границы и negative triggers |
| обязательное правило спрятано в reference | агент действует, не прочитав ограничение | поднять правило в entrypoint или always-on policy |
| entrypoint ссылается на «прочитать всё» | экономии контекста нет | привязать ресурсы к веткам и условиям |
| глубокая цепочка ссылок | детали читаются частично или пропускаются | ссылки на один уровень от entrypoint |
| чрезмерная фрагментация | растут tool calls и latency | объединить детали, используемые одним решением |
| discovery считается authorization | агент получает лишние полномочия | проверять permission перед read, execute и side effect |
| нет telemetry | ошибки selector неотличимы от ошибок reasoning | трассировать выбор и загрузку |

## Как проверять

Нужны evals не только итогового результата, но и маршрутизации:

| Метрика | Что показывает |
|---|---|
| Discovery recall | активировалась ли нужная возможность |
| Activation precision | не загрузились ли нерелевантные инструкции |
| Resource selectivity | прочитаны ли только нужные ресурсы |
| Context cost | сколько входных токенов добавлено на каждом уровне |
| Lookup latency | сколько времени и вызовов стоило раскрытие |
| Outcome quality | выполнена ли задача после выборочной загрузки |
| Safety miss rate | не было ли действия без policy или permission |

Минимальный eval-набор должен включать позитивные, негативные, неоднозначные и multi-capability запросы. Для каждого case полезно проверять не единственный допустимый trace, а обязательные события: правильную активацию, чтение критического ресурса, отсутствие лишних ресурсов и соблюдение security gate.

## Чем progressive disclosure не является

- **Не prompt caching:** caching удешевляет повтор стабильного префикса, но не решает, что должно попасть в контекст.
- **Не summarization:** summary уменьшает уже выбранный материал; progressive disclosure решает, выбирать ли его вообще.
- **Не RAG:** retrieval находит релевантные данные; progressive disclosure управляет уровнями доступа к ним.
- **Не context distillation:** [distillation](../advanced/agent-context-distillation.md) сжимает накопленное состояние между этапами.
- **Не permission model:** возможность обнаружить ресурс не означает право читать или исполнять его.
